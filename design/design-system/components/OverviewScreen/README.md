This — not a full-width Changes panel, not a full-width graph — is the window GitDesk actually opens to: BranchTree on the left, CommitGraph as the primary center content, and Git Changes docked on the right as its own fixed-width column, all three live at once. Earlier drafts of this system showed Changes and the graph as two screens a person switched between; that was wrong. A Git client's whole value is seeing the history you're about to add to while you write the commit that adds to it, so the two panels are peers sharing one window, not alternate views of it.

The dock is 360px, fixed, never fluid with the graph — the graph is where columns need room (a message wants to read past one line's worth of truncation before `Date`/`ID` even enter), so all the width a wider window gains goes to `.graph-pane`'s `flex:1`, never to the dock. `Git Changes` gets its own small header (`dock-head`) with a close glyph, because unlike the sidebar's sections it's a whole panel a person can dismiss — from the toolbar's panel-toggle icon or the `Commit`/`Repository` menu pair, which open and close this same dock rather than swap the main content. Closing it hands `.graph-pane` the full width; nothing else in the layout moves, which is the same fixed-band discipline `ChangesScreen`/`HistoryScreen` describe for the title bar, menu bar, toolbar and status bar.

Selecting a commit in the graph and staging a file in the dock are two views onto the same repository state, so their obvious interaction — committing what's staged appends a new row to the graph immediately, right beside the panel that just emptied — is this layout's real payoff over two separate screens: the person never loses sight of the history to see the effect of their own commit on it.
